# config/

这里放**业务人员可以直接改**的配置。改完重启服务生效，不需要改代码、不需要重新构建。

## prompts.json · 提示词

| 字段 | 作用 | 改了会怎样 |
|---|---|---|
| `version` | 版本标识，**必填** | 会写进每条引导的埋点；收到「它说错了」时靠它归因到具体某次改动 |
| `guide` | 逐屏办事引导的说话方式 | 影响「第 N 步该怎么说」 |
| `intent` | 一句话识别成哪件事 | 影响「听懂老人说什么」 |
| `slot` | 表单格怎么填 | 影响「姓名/身份证填进去」 |
| `question` | 政策问答的口吻 | 影响「问知识时怎么答」 |
| `plan` | 未收录事项的现场规划 | 影响「清单里没有的事怎么排路径」 |

**只写想改的字段**：比如只想调引导话术，就写 `{ "version": "v2", "guide": "..." }`，其余自动用内置默认值。

### 三条硬规则

1. **改内容必须同时改 `version`**。否则埋点里两版混在一起，「它说错了」查不出是哪一版说的。
2. **格式错会启动失败**，不会静默退回默认值。这是故意的：改了没生效却不报错，比报错难查得多。
3. **不热重载**。中途换提示词会让同一单前后两句话风格不一致；改完重启。

### 提示词里已经写死了「按人调整」

`guide` 的第 8 条要求按数字素养分三档给不同说法（低 15 字 / 中 25 字 / 高 35 字，各带例子）。
这条不是文风偏好，它决定了**记忆有没有用**：老人在界面上改了「怎么给您讲」，
最终必须落到这句话的长度和说法上，否则记忆就只是面板上的一行字。

改 `guide` 时别把这条删掉。删了，改档案就不再有任何反应——
这类「改了配置、界面变了、输出没变」的退化最难发现，`tests/prompt-schema.test.ts` 里有一条测试专门守着它。

### 想恢复出厂默认

```bash
npm run config:export   # 用代码里的内置值覆盖 prompts.json
```

## 还没外置的部分（诚实说明）

- **事项流程**（`src/core/domain/catalog.ts`）：12 条流程、材料清单、基线步数仍在代码里。
- **屏幕库**（`src/shared/screens.ts`）：37 屏的结构、文案、控件 id 仍在代码里。

这两块外置需要配套的校验（控件 id 必须真实存在、流程落点必须接得上下一节点），
否则业务人员改错一个 id，界面就会指到一个不存在的地方——**指错比不指更糟**。
所以它们暂留在代码里，由测试守（`tests/catalog.test.ts` 已断言「每个节点的落点就是下一节点的起点」）。
