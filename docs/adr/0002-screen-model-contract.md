# ADR-0002 · 以「屏幕模型」作为跨端统一契约

- 状态：已采纳
- 日期：2026-10-27
- 决策者：架构组

## 背景

Agent 需要知道「屏幕上有什么」，前端需要把界面画出来。这两件事在常规做法里是分开的：前端写 JSX，Agent 端另做一套屏幕描述（或截图 + OCR）。分离带来三类问题：

1. 两边不一致 —— Agent 指了一个前端根本没渲染的按钮；
2. 演示造假嫌疑 —— 评委有理由怀疑「AI 是照着预设答案演的」；
3. 迁移成本 —— 换到真机时，两套描述都要重写。

## 决策

用同一份数据结构 `shared/screens.ts` 同时驱动：

- **渲染**：`ScreenView` 按 `blocks` 逐块渲染（grid / list / form / dialog …）；
- **读屏**：服务端直接把同一 `blocks` 展开成控件清单喂给模型，并用 `SCREEN_CONTROL_INDEX` 校验目标控件是否存在。

配套约束：

- 流程图的每个 `targetControlId` 必须存在于对应屏幕（契约测试强制）；
- 服务端返回动作前二次校验控件存在性，非法即拒绝；
- `semantics` 字段以自然语言描述业务语义（「目标位于第 18 项，不在首屏」），让模型能生成「往下划」这类现场感表述。

## 后果

**正面**

- 「AI 假装看得见」的质疑被结构性消除：它读的和你看的是同一份数据；
- 控件不存在的失败模式在编译期/测试期被拦截，不会到用户面前；
- 迁移到真机只需替换数据源，接口语义不变。

**负面**

- 屏幕数据必须可枚举，无法覆盖任意第三方界面；
- 数据文件较大（17 屏），新增事项需同步维护两处（屏幕 + 流程），靠契约测试兜底。

## 迁移路径

生产环境由 Android `AccessibilityService` 输出节点树，映射为同构的 `ScreenModel`：

| 现有字段 | 真机来源 |
| --- | --- |
| `title` | 当前 Activity / 页面标题节点 |
| `blocks[].items[].label` | 节点 `text` 或 `contentDescription` |
| `blocks[].items[].id` | 节点稳定标识（resource-id 或结构路径哈希） |
| `semantics` | 规则生成：应用名 + 页面类型 + 可见项数量 |
| `risky` | 文案关键词 + 控件类型（支付/密码输入框） |

映射层属于基础设施，领域层无感。
