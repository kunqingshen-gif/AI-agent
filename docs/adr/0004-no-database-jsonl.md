# ADR-0004 · 参赛版不引入数据库，埋点落 JSONL

- 状态：已采纳（临时性决策）
- 日期：2026-10-28
- 决策者：架构组

## 背景

产品需要留存「这次办理走了几步、走错几次、护栏拦了几次」以及完整的决策链路，用于复盘、答辩演示与后续指标校准。

候选：SQLite / PostgreSQL / Redis / JSONL 文件。

## 决策

参赛版使用**进程内存存会话 + JSONL 追加写埋点**：

- 会话：`Map<sessionId, SessionState>`，随进程生命周期；
- 埋点：`.{DATA_DIR}/events-YYYY-MM-DD.jsonl`，一行一事件，字段为 `{type, sessionId, at, payload}`。

## 理由

1. **零依赖**：`better-sqlite3` 需要本地编译，在 Windows 答辩机上容易出问题；
2. **可演示**：`tail -f events-*.jsonl` 能实时展示 Agent 的行为链路，比翻数据库更有说服力；
3. **足够用**：单场演示的事件量在千级，追加写无压力，且天然按天分片；
4. **可替换**：埋点通过 `TelemetryPort` 接口注入，换 ClickHouse/Kafka 时应用层无感。

## 后果

**正面**：部署极简（一个 Node 进程 + 一个目录），答辩机可离线运行。

**负面与缓解**

| 问题 | 缓解 |
| --- | --- |
| 进程重启会话丢失 | 演示前不重启；生产替换为 Redis（抽 `SessionStore` 端口） |
| 指标只能按天聚合 | 提供 `/api/metrics` 内存计数；离线分析用脚本读 JSONL |
| 无并发控制 | 单进程顺序写；多副本部署需改为外部存储 |

## 触发重新评估的条件

满足任一条件即须替换：

- 需要跨设备继续办理（会话要跨进程）；
- 需要按用户维度做长期统计（超过单机文件可用范围）；
- 上线为正式服务（需审计留痕与数据生命周期管理）。
