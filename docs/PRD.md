## 1. 背景与问题

线上政务服务已实现「能办」，但对 60 岁以上人群，**办理过程本身构成了新门槛**。以低保对象定期复核为例，完整路径为：App 首页（12 宫格）→ 民政服务列表（24 项）→ 办理须知（长文）→ 表单（5 个必填项）→ 人脸核验 → 风控弹窗 → 受理结果。

四类失败在真实场景中反复发生，且**都不会告诉用户错在哪**：

1. **入口迷失**：点进同名近似入口（医保专区），翻找无果后放弃。
2. **同名混淆**：「临时救助申请」与「低保复核」是两个事项，界面文案高度相似。
3. **表单卡壳**：字段口径不清（「家庭共同生活人口数」是否含本人），填错被打回。
4. **高危环节失守**：人脸失败后遭遇电诈电话，被引导「转账验证」。

现有替代方案均无法覆盖「此刻这一步」：

| 方案 | 失效原因 |
| --- | --- |
| 子女远程指导 | 不可规模化；电话里说不清「那个蓝色按钮」是哪一个 |
| 12345 热线 | 看不到屏幕，只能听描述，无法定位到控件 |
| 图文/视频教程 | 与用户手机上的应用版本、界面布局不一致 |
| 政务 App 长辈版 | 只解决字号与配色，未解决「下一步点哪」 |

## 2. 产品目标

**让一位不熟悉智能手机的老人，在不求助他人的情况下，独立完成一件需要跨 3 个页面、填写 5 个字段、经过 2 次实名校验的政务事项。**

### 2.1 目标（本期）

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G1 | 口语到事项的识别准确 | 4 个事项的口语样本识别正确率 ≥ 90% |
| G2 | 引导动作指向正确 | 流程节点与控件契约测试 100% 通过 |
| G3 | 走错后可被拉回 | 走错后 1 步内回到正轨 |
| G4 | 模型不可用时仍可用 | 断网/无密钥状态下全流程可走完 |
| G5 | 高危动作零代操作 | 六类护栏节点 100% 降级为本人确认 |

### 2.2 非目标（本期明确不做）

- **不做开放式自动规划**：不为未知事项现场生成流程，宁可窄而稳。新增事项走「补流程图 + 契约测试」流程。
- **不做代办**：不代填身份证/银行卡、不代刷脸、不代支付、不代输验证码。
- **不做语音唤醒常驻**：本期以页面内语音输入为主，系统级悬浮窗属于下一阶段。
- **不做多端同步**：会话状态在单进程内存，断电即失效（见 ADR-0004）。

## 3. 用户与场景

### 3.1 用户角色

| 角色 | 特征 | 核心诉求 | 使用频率 |
| --- | --- | --- | --- |
| 办事老人（主要） | 60–80 岁，数字素养低，独居比例高 | 有人陪着点完，别点错、别被骗 | 每半年 1–2 次 |
| 异地子女（次级） | 25–45 岁，远程协助父母 | 一个能替我「在场」的东西 | 每月 1–3 次 |
| 社区/窗口人员（机构） | 一人对接上百位对象 | 分流重复咨询，只接真需要人的个案 | 每日 |

### 3.2 主用户旅程（低保复核）

| 阶段 | 用户行为 | 痛点 | 产品介入 |
| --- | --- | --- | --- |
| 触发 | 收到社区通知「手机上办」 | 不知道从哪进 | 语音说出需求即可 |
| 找入口 | 在 12 宫格与 24 项列表中找 | 反复试错 | 高亮到具体那一行 |
| 读须知 | 面对 3 段长文 | 被劝退 | 一句话概括「这页告诉您带什么材料」 |
| 填表 | 5 个必填项 | 口径不清、打字慢 | 逐格引导 + 一键预填 + 口语填表 |
| 核验 | 人脸 + 风控弹窗 | 不懂在做什么 | 解释 + 停手 + 反诈提示 |
| 收尾 | 拿到受理编号 | 不会保存 | 播报编号并提示留存 |
| 失败 | 卡住 | 说不清自己在哪一步 | 生成带上下文的话术 |

### 4.2 关键交互规则

**管家四通道与办事主线的优先级。** 一次输入依次经过：反诈判别 → 办前体检 → 协办 → 守护日历 →
知识问答 → 意图识别 → 现场规划。反诈排在最前，因为漏判的代价不可逆；
知识问答排在办事之前，因为「要带什么材料」这类问题要的是答案不是流程。
任何一环判定不成立就安静地往下走，不打扰、不硬答。


1. **一次只指一个控件**：任何一步不得同时给出多个可点击目标。
2. **指令必须引用屏幕原字**：如「点『开始办理』」，不得使用「进入办理页面」这类需要推理的表述。
3. **指令长度上限 60 字，播报上限 40 字**，超限自动回退模板。
4. **护栏节点不展示「帮您点」类按钮**，只展示解释与风险提示。
5. **点错不阻断**：模拟真实应用照常跳转，由 Agent 事后纠偏。
6. **引导未就绪时点击不计数**：避免把「用户手快」误判为「用户迷路」。
7. **每一步都要有一个位置固定的大按钮**：底部「下一步」必须与当前高亮目标严格一致，
   文案引用控件原名；目标不存在（纯阅读节点、弹窗页）时整条撤下，不留空壳按钮。
8. **链路必须首尾相接**：每个流程节点的落点必须正好是下一节点的起点，由契约测试守住——
   否则「下一步」会在中途消失，老人被迫自己在一长串服务里翻。

### 4.3 边界与异常

| 场景 | 处理 |
| --- | --- |
| 模型超时 / 非 JSON / 违规内容 | 回退规则模板，埋点记录 `llm.fallback` |
| 用户连续 3 次同屏无进展 | 判定卡死，触发救援话术 |
| 用户主动求助 | 立即生成话术，不改变当前引导 |
| 会话不存在 | 返回 404，前端提示重新开始 |
| 未开放入口 | 轻提示，不跳转 |
| 表单必填缺失 | 标红缺失项并回到对应格 |

## 5. 非功能需求

| 类别 | 要求 | 实现 |
| --- | --- | --- |
| 响应延迟 | 规则路径 P90 < 50ms；模型路径有硬上限 | 规则端到端实测 P50 2.3ms / P90 6.1ms；模型 P50 2.0s / P90 2.4s，8s 硬超时后瞬时降级 |
| 可用性 | 模型不可用时功能不降级为不可用 | 三级兜底 |
| 安全 | 入参校验、限流、日志脱敏 | zod + rate-limit + pino redact |
| 隐私 | 不落库证件号原文 | 埋点仅记录行为与耗时 |
| 可维护 | 新增事项不修改引擎代码 | 事项以数据（流程节点）声明 |
| 可测试 | 核心逻辑脱离 HTTP 可测 | 领域层纯函数 + 端口注入 |

## 6. 成功指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 任务完成率 | 进入流程后完成办理的比例 | ≥ 80%（30 人测试） |
| 平均引导步数 | 完成一次事项的引导次数 | ≤ 基线步数 |
| 走错次数 | 触发 back 动作次数 | ≤ 1 |
| 单步迟疑时长 | 指令下发到用户点击的间隔 | ≤ 15s |
| 护栏守约率 | 高危节点零代操作 | 100% |

> 当前版本已实现机器可测指标（延迟、护栏命中、纠偏次数），人工可用性指标待 11 月测试补齐。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 无障碍权限受限 | 无法读屏，产品失效 | 优先与政务平台共建（内嵌模式不需要无障碍权限） |
| 模型幻觉导致误指 | 信任崩塌 | 已收录事项决策不由模型做；未收录事项的规划必须过屏幕契约（控件必须真实存在）与语义相关闸门，不符即截断并如实告知 |
| 规划跨事项误用 | 把信息填进别人的事项 | 语义闸门按「屏幕标题/控件标签 vs 事项名」判断相关性；生产环境改为以事项编码硬约束（见说明书 7.4） |
| 老人过度依赖 | 数字能力进一步退化 | 每步给出「为什么」，逐步培养理解；提供「自己试试」模式（规划中） |
| 事项流程变更 | 引导失效 | 契约测试 + 节点版本化 |
| 合规审查 | 上线受阻 | 三个不做的硬边界 + 数据最小化 |
